# Script Flow — Analysis ↔ Component Consistency Plan

## Purpose

Fix three related problems in the script flow:

1. **Analysis and components show different numbers** for the same question.
2. **Charts render with `N/A` axes or no data** (bad axis/value keys, KPI showing the wrong value).
3. **Components and analysis can drift between replays** of the same script because components are re-generated by an LLM on every run.

This plan also documents **how post-JS transformed data reaches components today**, because that mechanism constrains the fix.

> Related: `RECIPE-ARCHITECTURE.md` §11 ("Component Generation with Scripts") already describes the end state (recipe stores presentation config, deterministic assembly on replay, no component LLM call). That design was never built — `ScriptRecipe` has no component fields and `generateScriptComponents` runs an LLM on every replay. Phase 3 below builds it.

---

## 1. Symptom (observed)

Question: *"verify remaining + consumed shelf life sums consistently for SO-82280"*. Script returns 3 device rows.

| Surface | Value shown | Where it comes from |
|---|---|---|
| Analysis text | "All three devices sum to exactly **188.54 days**" | LLM computed `remainingShelfLifeDays + consumedShelfLifeDays` in prose |
| KPI card "TOTAL SHELF LIFE (ALL DEVICES)" | **159.54 days** | `DynamicKPICard` rendered `data[0].remainingShelfLifeDays` |

`188.54` is `159.54 + 29` (and `165.64 + 22.9`, `176.94 + 11.6` — all equal 188.54). The analysis did arithmetic that **does not exist as a column**, and the KPI fell back to the first row.

---

## 2. Root cause

The analysis and the components derive their numbers from **two independent paths over the same raw rows**:

- **Analysis** = an LLM that reads the rows and can do arbitrary arithmetic. It can produce a number (`188.54`) that is not present in the data.
- **Components** = the frontend re-runs the query (by `queryId`) and renders **raw columns** — `data[0][valueKey]` for a KPI, or a simple frontend `sum`/`avg`/`count`. It can only show values that exist as columns (or trivial aggregates of them).

So the discrepancy is a **data-provenance problem**, not an "agent count" problem. Merging analysis and component generation into one agent does not fix it, because the frontend still renders columns, not prose.

### Three concrete defects

**A. KPI shows row 0, not an aggregate.**
`frontend/src/shared-modules/DynamicKPICard/index.tsx:762` — with no `config.aggregation` set, the value is `getCaseInsensitiveValue(data[0], valueKey)`. The card *supports* `sum`/`avg`/`count`/`min`/`max` (lines ~600–668) via `config.aggregation` + `config.aggregationField`, but **the `script-components` prompt never mentions these fields**, so the LLM never sets them. A "TOTAL (ALL DEVICES)" card silently shows the first row.

**B. The analysis cites values that are not columns.**
`188.54` (`remaining + consumed`) is a derived number. No component config can reproduce it, because it is not a column and not a trivial aggregate of one. It exists only in the analysis LLM's text.

**C. Charts: `N/A` axes / empty.**
The bar chart is already case-insensitive (`DynamicBarChart/index.tsx:81`) and auto-detects swapped keys (`:284–299`). So the usual cause is **not casing** — it is the LLM picking a `xAxisKey`/`yAxisKey`/`valueKey` that **does not exist** in the data (hallucinated, or a derived column the script never emitted), or a `yAxisKey` that points at a TEXT column → `parseFloat` → `NaN` → empty chart.

## 3. How transformed (post-JS) data reaches components today

This is load-bearing for the fix, so it is documented explicitly.

A script may call `ctx.runTool(...)` and/or `ctx.query(toolId, sql)`, then transform the rows in JS and `return { data, count }`.

1. The child's `RESULT` message carries `executedQueries` that contain **only real `ctx.query` SQL calls**. `runTool` results and the final transformed `data` are **not** in `executedQueries`.
2. `withSynthesizedFinalData()` (`sdk-nodejs/src/userResponse/scripts/script-runner.ts:506`) detects a transform: if the final columns differ from the raw SQL columns, **or** there were no SQL queries at all (e.g. `runTool`-only / pure-JS), it **prepends a synthetic entry**:
   ```
   { sourceId: 'computed:_final', sourceName: 'Script final dataset', virtual: true, data: <transformed rows>, count }
   ```
3. `generateScriptComponents` (`script-component-generator.ts`) stores each query's rows in the in-memory `queryCache` → gets a `queryId`. For `virtual` entries it sets the component's `toolId` to the **`script_dataset` sentinel** (`:209`).
4. The frontend renders → `executeByQueryId({ toolId: 'script_dataset', queryId })` → the backend **short-circuits and returns the cached transformed rows** (no SQL re-run, because no SQL reproduces a JS transform).

### The fragility this creates

- The transformed dataset lives **only** in the in-memory `queryCache` (TTL ~10 min, LRU cap 5000 — `sdk-nodejs/src/utils/query-cache.ts:26–27`).
- Raw-SQL components can rehydrate by re-registering their SQL (`_queryMap` → `rehydrateCachedComponent`, `agent-user-response.ts:93`). **`script_dataset` components cannot** — there is no SQL to replay.
- When the cache entry expires, the component shows *"Script dataset expired."* The only recovery is **re-running the whole script** — which `hasExpiredScriptDataset` (`agent-user-response.ts:61`) now triggers by falling through to the matcher.

**Conclusion: transformed data is never reproduced by SQL — it is reproduced by replaying the script.** Therefore the component recipe (Phase 3) must store the *binding* (component type + column mapping + which source/virtual dataset), **never the data**. On every replay the script runs, produces fresh rows, and the stored binding is rebound to a fresh `queryId`.

---

## 4. The fix

Build order: **Phase 1 + Phase 2 first** (fix the visible bugs in both the replay and fresh paths), then **Phase 3** (make it deterministic and free on replay).

The component subagent idea is explicitly **out of scope** — it does not address the frontend-renders-columns reality, and the hot path (tier-`high` replay) has no MainAgent at all.

---

### Phase 1 — Deterministic validate-and-repair in the component generator

**Goal:** kill `N/A` axes, empty charts, and KPI-row-0. No new LLM call for the common case.

**File:** `sdk-nodejs/src/userResponse/scripts/script-component-generator.ts`
**Prompt:** `backend/.prompts/script-components/system.md`

We already know every column name and type from `q.data[0]` (`:69–75`). After the LLM returns its component picks, run a deterministic pass per component **before** building the `Component`:

```ts
// columns: Map<lowercaseName, { name: string; type: 'NUMBER'|'TEXT'|'DATE'|'BOOLEAN' }>
function validateAndRepair(comp, columns, rowCount) {
  const cfg = comp.props?.config ?? {};

  // 1. Resolve every key to a REAL column (case-insensitive). Drop unknowns.
  const resolve = (k) => columns.get(String(k).toLowerCase())?.name; // undefined if missing
  for (const key of ['xAxisKey','yAxisKey','valueKey','nameKey','seriesKey','groupBy','aggregationField']) {
    if (cfg[key]) {
      const real = resolve(cfg[key]);
      if (real) cfg[key] = real; else delete cfg[key];   // unknown column → drop
    }
  }
  if (Array.isArray(cfg.metricKeys)) {
    cfg.metricKeys = cfg.metricKeys.map(resolve).filter(Boolean);
  }

  // 2. Enforce type roles (don't rely on the chart's runtime swap — bake it in).
  //    category/name/x → TEXT;  value/metric/y → NUMBER.
  // 3. KPI aggregation: if title/intent implies an aggregate AND rowCount > 1,
  //    require aggregation + aggregationField, else the card shows data[0].
  if (isKpi(comp) && rowCount > 1 && /total|all|sum|average|avg|count|overall/i.test(comp.props?.title ?? '')) {
    if (!cfg.aggregation) {
      cfg.aggregation = 'sum';                 // or 'avg'/'count' from title keyword
      cfg.aggregationField = cfg.aggregationField ?? cfg.valueKey ?? firstNumericColumn(columns);
    }
  }

  // 4. If a required key for this component type can't be resolved → signal "unfixable".
  return isRenderable(comp, cfg) ? { ...comp, props: { ...comp.props, config: cfg } } : null;
}
```

- Components the deterministic pass marks **unfixable** → one LLM repair attempt as a fallback (re-pick column / change type), then drop if still bad.
- Prompt change: add `aggregation` / `aggregationField` to the KPI section of `script-components/system.md` so the LLM sets them itself when it can.

**Acceptance:** every emitted component's config keys exist in the data; numeric keys point at NUMBER columns; "total/all/avg" KPIs carry an aggregation. No silent row-0 KPIs, no `N/A` axes from missing columns.

### Phase 2 — Script is the single source of truth for numbers

**Goal:** the analysis can only state numbers that the components can also show.

- **Authoring policy** — `backend/.prompts/agent-main/system.md` (the "Authoring a Reusable Script" section): *every number the answer will state must be a returned column.* If the answer is about "total shelf life," the script must emit `totalShelfLifeDays` (e.g. `remaining + consumed`) as a column. No answer-bearing arithmetic left for the analysis LLM.
- **Analysis constraint** — `backend/.prompts/script-analysis/system.md`: cite only values present in the dataset columns; do not compute new aggregates in prose.

Once the derived value is a real column, both the analysis (reads the column) and the KPI (renders/aggregates the column) reference the same number. The `188.54 vs 159.54` class of bug disappears.

**Acceptance:** for a transformed-data question, the headline number in the analysis equals the number rendered by the corresponding component.

### Phase 3 — Component recipe: persist once, replay deterministically

**Goal:** the script generates the components. Eliminate the per-replay component LLM call and the per-replay drift. This is `RECIPE-ARCHITECTURE.md` §11.

**Files:** `types.ts`, `script-store.ts`, `script-component-generator.ts`, `agent-user-response.ts`.

1. **Add a spec type and a recipe field** (`types.ts`):
   ```ts
   export interface ScriptComponentSpec {
     componentType: string;          // registered id or name, e.g. "bar-chart" / "DynamicBarChart"
     sourceRef: string;              // sourceId to bind, or 'computed:_final' for the post-JS dataset
     title: string;
     description?: string;
     config: Record<string, any>;    // validated keys + aggregation, all referencing real columns
   }
   // on ScriptRecipe:
   components?: ScriptComponentSpec[];
   ```

2. **Persist at authoring** — after `execute_script` succeeds and Phase 1 validates the picks, store the validated specs on the recipe (`script-store.ts` save path, alongside `scriptBody`). Store **bindings only, never data**.

3. **Deterministic replay** (`agent-user-response.ts`, tier-`high` path): after `runScript` returns fresh `executedQueries`, **skip the component LLM**:
   ```ts
   for (const spec of recipe.components ?? []) {
     const q = scriptResult.executedQueries.find(e => e.sourceId === spec.sourceRef)
            ?? scriptResult.executedQueries.find(e => e.virtual); // computed:_final fallback
     if (!q) continue;
     const queryId = queryCache.storeQuery(q.sql, { data: q.data, count: q.count });
     const toolId  = q.virtual ? 'script_dataset' : q.sourceId;
     components.push(buildComponent(spec, { toolId, queryId }));
   }
   ```
   Columns cannot mismatch: the same script produces the same shape, and the spec was validated against that shape at authoring.

4. **Cheap re-validation on replay** — confirm the fresh rows still contain the spec's keys. If the shape drifted (script was hand-edited), fall back to a single `generateScriptComponents` run + re-store the new specs.

5. **Adaptive override preserved** — an explicit "show that as a pie chart" can override `componentType` for that turn; still deterministic, no full regeneration.

**Acceptance:** replaying a saved script issues **zero** component-generation LLM calls; the rendered components are byte-identical in structure across replays (only `queryId` and data change).

## 5. Build & deploy notes

- The SDK is consumed by the backend from a **local path**, not `node_modules` republish. SDK changes go live via `pnpm build` in `sdk-nodejs/` + backend restart.
- `script-bootstrap` runs in the child via `tsx`; if its source changes, the built `dist/userResponse/scripts/script-bootstrap.js` must be rebuilt.
- Frontend (KPI/chart components) runs from the **built Vite bundle**; the KPI/chart files are already case-insensitive and aggregation-capable, so Phases 1–3 need **no frontend change** in the common case. If we touch a shared-module component, run the frontend `pnpm build` + reload.

## 6. Test checklist

1. Transformed-data question (the SO-82280 shelf-life case): analysis headline number == KPI value.
2. Ranking question → horizontal bar chart renders with correct axes, no `N/A`.
3. "Total / average across all X" KPI → aggregates, does not show row 0.
4. Replay the same question → logs show no component LLM call; components match the first run.
5. Let the `queryCache` entry expire, then re-ask → script replays, `script_dataset` components hydrate from fresh data (no "expired" sentinel).
6. Parameterized script with a different param value → same component shapes, new data.

---

## 7. Out of scope

- **Component generation as a MainAgent subagent.** Does not fix the frontend-renders-columns reality; the tier-`high` replay path has no MainAgent, so a fix there would miss the hot path. The validation + recipe live in the component generator instead, shared by all paths.
- Storing transformed datasets durably (beyond `queryCache`). Replay is the source of truth for post-JS data.
- Component-embedding pre-filter / consolidation (covered elsewhere).
